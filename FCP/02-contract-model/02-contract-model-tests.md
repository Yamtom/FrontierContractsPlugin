# Contract Model — Чеклист тестування

> **⚠ Нагадування для AI-агента:**
> Якщо будь-який пункт цього документа змінюється (додається кейс, виправляється опис, змінюється очікуваний результат) — **обов'язково**:
> 1. Додай запис у секцію `## Лог змін` внизу файлу (дата + короткий опис).
> 2. Якщо змінюється алгоритм — звір із [02-contract-model.md](./02-contract-model.md) та оновлюй синхронно.
> 3. Не видаляй старі записи логу — лише додавай нові зверху.

## ContractTemplate

### CT-01 — `maxPlayers()` повертає значення з YAML
- [ ] Виконано
- **Кроки:** Адмін встановлює `max-simultaneous-players: 3` у файлі contracts.yml для певного контракту. Гравець відкриває меню дошки.
- **Очікується:** У деталях контракту відображається, що одночасно можуть брати участь 3 гравці.

### CT-02 — `maxPlayers()` за замовчуванням = 1
- [ ] Виконано
- **Кроки:** Адмін не вказує поле `max-simultaneous-players` у contracts.yml. Гравець відкриває меню дошки.
- **Очікується:** Контракт доступний лише одному гравцю одночасно; у деталях вказано 1 слот.

### CT-03 — `maxPlayers()` не може бути < 1
- [ ] Виконано
- **Кроки:** Адмін встановлює `max-simultaneous-players: 0` у contracts.yml. Перший гравець приймає контракт.
- **Очікується:** Контракт прийнятий успішно. Другий гравець не може прийняти той самий оффер — єдиний слот зайнятий.

### CT-04 — `createOffer()` передає `maxPlayers` у ContractOffer
- [ ] Виконано
- **Кроки:** Адмін налаштовує контракт з `max-simultaneous-players: 3`. Дошка генерує оффер. Гравець відкриває меню.
- **Очікується:** У деталях оффера показано, що доступно 3 слоти для учасників.

### CT-05 — `createOffer()` ініціалізує `activePlayers = 0`
- [ ] Виконано
- **Кроки:** На дошці щойно з'явився новий оффер (ніхто ще не прийняв). Гравець відкриває деталі контракту.
- **Очікується:** Показано 0 активних учасників; всі слоти вільні.

## ContractOffer

### CO-01 — `canAccept()` = true коли `activePlayers < maxPlayers`
- [ ] Виконано
- **Кроки:** Контракт має 3 слоти, 2 вже зайнято. Третій гравець відкриває меню дошки та натискає на оффер.
- **Очікується:** Кнопка прийняття активна; гравець може прийняти контракт.

### CO-02 — `canAccept()` = false коли `activePlayers == maxPlayers`
- [ ] Виконано
- **Кроки:** Контракт має 3 слоти, всі 3 зайняті. Четвертий гравець відкриває меню дошки.
- **Очікується:** Контракт позначено як заповнений; кнопка прийняття недоступна.

### CO-03 — `incrementActivePlayers()` збільшує на 1
- [ ] Виконано
- **Кроки:** Контракт має 1 активного учасника (з 3). Ще один гравець приймає оффер.
- **Очікується:** Кількість вільних слотів зменшується на 1; інші гравці бачать оновлену кількість доступних місць.

### CO-04 — `decrementActivePlayers()` зменшує на 1
- [ ] Виконано
- **Кроки:** Контракт має 2 активних учасники. Один з них завершує або скасовує контракт.
- **Очікується:** Кількість активних учасників зменшується до 1; звільнений слот знову доступний.

### CO-05 — `decrementActivePlayers()` не йде нижче 0
- [ ] Виконано
- **Кроки:** Останній учасник контракту завершує або скасовує його. Сервер оновлює лічильник (активних = 0).
- **Очікується:** Лічильник залишається на 0; жодних помилок у консолі сервера.

### CO-06 — `setActivePlayers()` нормалізує від'ємне значення
- [ ] Виконано
- **Кроки:** Під час запуску сервер виявляє пошкоджене від'ємне значення активних учасників у базі даних.
- **Очікується:** Значення нормалізується до 0; сервер завантажується без помилок, контракт доступний для прийняття.

## PlayerContract

### PC-01 — Конструктор зберігає `type`
- [ ] Виконано
- **Кроки:** Гравець приймає контракт типу "Доставка" (DELIVERY) з меню дошки.
- **Очікується:** У списку активних контрактів тип відображається як "Доставка".

### PC-02 — `type` за замовчуванням = DELIVERY при null
- [ ] Виконано
- **Кроки:** У файлі contracts.yml не вказано тип для контракту. Гравець приймає його з меню.
- **Очікується:** Контракт поводиться як тип "Доставка"; вимоги ресурсів відображаються коректно.

### PC-03 — Конструктор копіює список `requirements`
- [ ] Виконано
- **Кроки:** Гравець приймає контракт з 2 вимогами (наприклад, 32 OAK_LOG та 16 OAK_PLANKS). Адмін редагує шаблон після прийняття гравцем.
- **Очікується:** Вимоги у контракті гравця залишаються незмінними — 32 OAK_LOG та 16 OAK_PLANKS.

### PC-04 — `isFulfilled()` = false коли requirements порожній
- [ ] Виконано
- **Кроки:** Гравець приймає контракт, у якого відсутні вимоги ресурсів. Відкриває деталі контракту.
- **Очікується:** Контракт не вважається виконаним; кнопка завершення недоступна.

### PC-05 — `isFulfilled()` = false коли хоча б одна вимога незакрита
- [ ] Виконано
- **Кроки:** Гравець виконав першу з двох вимог. Відкриває деталі контракту.
- **Очікується:** Контракт позначено як незавершений; нагорода ще не нарахована.

### PC-06 — `isFulfilled()` = true коли всі вимоги виконані
- [ ] Виконано
- **Кроки:** Гравець здає останню порцію ресурсів, виконуючи всі вимоги.
- **Очікується:** Контракт автоматично завершується; гравець отримує нагороду та повідомлення у чаті.

### PC-07 — `findRequirement(Material)` повертає відповідну вимогу
- [ ] Виконано
- **Кроки:** Гравець тримає OAK_LOG у руці та правим кліком натискає на знак дошки, де є контракт з вимогою OAK_LOG×32.
- **Очікується:** Здача OAK_LOG зараховується для правильного контракту; прогрес оновлено.

### PC-08 — `findRequirement(Material)` повертає null при відсутності
- [ ] Виконано
- **Кроки:** Гравець тримає STONE та натискає на дошку, де жоден активний контракт не вимагає STONE.
- **Очікується:** Гравець отримує повідомлення, що цей ресурс не підходить жодному контракту.

### PC-09 — `findRequirement(null)` повертає null без NPE
- [ ] Виконано
- **Кроки:** Гравець натискає на знак дошки з порожньою рукою (без предмета).
- **Очікується:** Відкривається меню дошки без помилок; жодних повідомлень про збій у консолі.

## ContractService — accept()

### CS-AC-01 — LOCAL accept при вільному слоті → створює PlayerContract
- [ ] Виконано
- **Кроки:** Гравець відкриває меню місцевої дошки. Оффер має 3 слоти, жоден не зайнятий. Гравець натискає "Прийняти".
- **Очікується:** Контракт з'являється у списку активних контрактів гравця; у чаті — повідомлення про успішне прийняття.

### CS-AC-02 — LOCAL accept при зайнятих слотах → `errors.contract-full`
- [ ] Виконано
- **Кроки:** Оффер має 1 слот, вже зайнятий. Інший гравець натискає "Прийняти" у меню.
- **Очікується:** Гравець бачить повідомлення про заповнені слоти; контракт не додається до активних.

### CS-AC-03 — accept LOCAL збільшує `activePlayers`
- [ ] Виконано
- **Кроки:** Оффер має 3 вільних слоти. Гравець успішно приймає контракт.
- **Очікується:** Кількість доступних слотів у меню зменшується на 1; інші гравці бачать оновлений стан.

### CS-AC-04 — accept LOCAL зберігає особисту копію requirements
- [ ] Виконано
- **Кроки:** Гравець приймає оффер з вимогою 32 OAK_LOG. Відкриває деталі свого контракту.
- **Очікується:** Вимога відображається як 0/32 OAK_LOG; прогрес розпочинається з нуля.

### CS-AC-05 — GLOBAL accept заборонений повторно → `errors.already-accepted`
- [ ] Виконано
- **Кроки:** Гравець вже виконав або провалив глобальний контракт. Намагається прийняти той самий оффер ще раз.
- **Очікується:** Гравець бачить повідомлення, що вже брав участь у цьому контракті; повторне прийняття не відбувається.

### CS-AC-06 — LOCAL accept дозволяє знову прийняти після виконання
- [ ] Виконано
- **Кроки:** Гравець виконав місцевий контракт і отримав нагороду. Знову відкриває меню тієї самої дошки.
- **Очікується:** Той самий оффер доступний для повторного прийняття; кількість слотів оновлена.

### CS-AC-07 — accept при неактивному оффері → `errors.unavailable-offer`
- [ ] Виконано
- **Кроки:** Адмін відключив оффер або термін його дії минув. Гравець намагається прийняти з меню.
- **Очікується:** Гравець отримує повідомлення, що контракт більше недоступний; прийняття не відбувається.

## ContractService — deliverToBoard()

### CS-DL-01 — Успішна часткова доставка
- [ ] Виконано
- **Кроки:** Гравець прийняв контракт з вимогою 32 OAK_LOG (здано 0). Тримаючи 10 OAK_LOG у руці, правим кліком натискає на знак дошки.
- **Очікується:** 10 OAK_LOG знімаються з інвентарю; у чаті повідомлення про прогрес "10/32 OAK LOG".

### CS-DL-02 — Повна доставка → нагорода
- [ ] Виконано
- **Кроки:** Вже здано 22 з 32 OAK_LOG. Гравець тримає 10 OAK_LOG і натискає на знак дошки.
- **Очікується:** 10 OAK_LOG знімаються; контракт автоматично завершується; гравець отримує нагороду та повідомлення у чаті.

### CS-DL-03 — Чужий матеріал → `errors.no-matching-resource`
- [ ] Виконано
- **Кроки:** Контракт вимагає OAK_LOG. Гравець тримає STONE та натискає на знак дошки.
- **Очікується:** Жодних предметів не знімається; гравець отримує повідомлення, що цей ресурс не підходить жодному контракту.

### CS-DL-04 — Немає активного контракту для дошки → `errors.no-matching-resource`
- [ ] Виконано
- **Кроки:** Гравець не приймав жодного контракту цієї дошки. Тримає будь-який предмет і натискає на знак.
- **Очікується:** Жодних змін в інвентарі; повідомлення, що немає активного контракту для здачі.

### CS-DL-05 — Заборона часткової здачі → `errors.full-delivery-required`
- [ ] Виконано
- **Кроки:** Контракт позначено як "лише повна здача". Вимога: 32 OAK_LOG. Гравець тримає 10 і натискає на дошку.
- **Очікується:** Жодних предметів не знімається; повідомлення, що потрібно здати всю кількість (32) за один раз.

### CS-DL-06 — Доставка не переповнює `deliveredAmount`
- [ ] Виконано
- **Кроки:** Вже здано 30 з 32 OAK_LOG. Гравець тримає стек з 64 OAK_LOG і натискає на дошку.
- **Очікується:** З інвентарю знімається рівно 2 OAK_LOG; у гравця залишається 62 одиниці.

## ContractService — rewardBoardContract()

### CS-RW-01 — Нараховується базова нагорода без deathless
- [ ] Виконано
- **Кроки:** Гравець виконував контракт і помер хоча б раз. Здає останній ресурс і завершує контракт.
- **Очікується:** Гравець отримує базову нагороду; у чаті немає згадки про бонус за безсмертність.

### CS-RW-02 — Deathless-бонус нараховується коли `deathless == true`
- [ ] Виконано
- **Кроки:** Гравець виконав контракт, жодного разу не померши. Множник безсмертності = ×1.2.
- **Очікується:** Гравець отримує нагороду з бонусом ×1.2; у чаті повідомлення про бонус за безсмертність.

### CS-RW-03 — `activePlayers` зменшується після нагороди
- [ ] Виконано
- **Кроки:** Контракт мав 2 активних учасники. Один виконує та отримує нагороду.
- **Очікується:** Кількість активних учасників зменшується до 1; звільнений слот стає доступним для нових учасників.

### CS-RW-04 — `contract.status() == CLAIMED` після нагороди
- [ ] Виконано
- **Кроки:** Гравець виконує контракт і отримує нагороду.
- **Очікується:** Контракт зникає зі списку активних; при спробі прийняти повторно він відображається як вже виконаний.

### CS-RW-05 — Контракт прибирається з `openContracts` після нагороди
- [ ] Виконано
- **Кроки:** Гравець отримав нагороду за виконаний контракт.
- **Очікується:** Контракт більше не відображається у списку активних контрактів гравця.

## ContractService — abandon()

### CS-AB-01 — Успішне abandon → status FAILED
- [ ] Виконано
- **Кроки:** Гравець відкриває список активних контрактів і натискає "Відмовитися" або вводить відповідну команду.
- **Очікується:** Контракт зникає з активних; у чаті повідомлення про скасування і штраф репутації.

### CS-AB-02 — `activePlayers` зменшується після abandon (LOCAL)
- [ ] Виконано
- **Кроки:** Місцевий контракт мав 2 активних учасники. Один відмовляється.
- **Очікується:** Звільнений слот відображається як доступний; другий гравець бачить оновлений лічильник.

### CS-AB-03 — GLOBAL abandon не змінює `activePlayers`
- [ ] Виконано
- **Кроки:** Гравець відмовляється від глобального контракту.
- **Очікується:** Кількість глобальних слотів не змінюється; нараховується штраф репутації.

### CS-AB-04 — abandon при відсутньому контракті → `errors.no-such-contract`
- [ ] Виконано
- **Кроки:** Гравець намагається скасувати контракт, якого не приймав (наприклад, вводить неправильний ідентифікатор).
- **Очікується:** Гравець отримує повідомлення про помилку; жодних змін у стані.

## ContractService — cleanupExpiredContent()

### CS-CL-01 — Прострочений ACTIVE → FAILED
- [ ] Виконано
- **Кроки:** Час виконання активного контракту гравця сплинув. Сервер проводить регулярну перевірку.
- **Очікується:** Контракт автоматично позначається як провалений; якщо гравець онлайн — отримує повідомлення у чаті.

### CS-CL-02 — `activePlayers` зменшується для LOCAL після cleanup
- [ ] Виконано
- **Кроки:** Місцевий контракт має 2 активних учасники. Один пропустив дедлайн. Сервер проводить очищення.
- **Очікується:** Кількість активних учасників зменшується до 1; звільнений слот стає доступним.

### CS-CL-03 — Прострочений контракт прибирається з `openContracts`
- [ ] Виконано
- **Кроки:** Прострочений контракт гравця очищено сервером.
- **Очікується:** Контракт зникає зі списку активних; більше не відображається у меню гравця.

### CS-CL-04 — Онлайн-гравець отримує повідомлення `contracts.failed-expired`
- [ ] Виконано
- **Кроки:** Гравець онлайн, але не встиг виконати контракт до дедлайну.
- **Очікується:** У чаті з'являється повідомлення про провал контракту з його назвою.

## StorageService — Contract Model

### SS-CM-01 — `saveOffer` / `loadOffers` roundtrip з `max_players` і `active_players`
- [ ] Виконано
- **Кроки:** Оффер з 3 слотами та 1 активним учасником існує на сервері. Сервер перезапускається.
- **Очікується:** Після перезапуску оффер зберігає 3 слоти та 1 активного учасника.

### SS-CM-02 — `savePlayerContract` / `loadOpenContracts` roundtrip з `type`
- [ ] Виконано
- **Кроки:** Гравець прийняв контракт типу "Доставка". Сервер перезапускається.
- **Очікується:** Після перезапуску контракт гравця залишається типу "Доставка" та продовжує відображатись у активних.

### SS-CM-03 — `loadOpenContracts` правильно десеріалізує `requirements_blob` з `deliveredAmount`
- [ ] Виконано
- **Кроки:** Гравець вже здав 15 OAK_LOG з 32 необхідних. Сервер перезапускається.
- **Очікується:** Після перезапуску у деталях контракту показано прогрес 15/32 OAK_LOG.

### SS-CM-04 — Міграція: стара DB без `max_players` → за замовчуванням 1
- [ ] Виконано
- **Кроки:** Плагін оновлено зі старої версії (без підтримки кількох учасників). Перший запуск після оновлення.
- **Очікується:** Сервер запускається без помилок; всі існуючі оффери мають 1 слот за замовчуванням.

### SS-CM-05 — Міграція: стара DB без `type` у player_contracts → DELIVERY за замовчуванням
