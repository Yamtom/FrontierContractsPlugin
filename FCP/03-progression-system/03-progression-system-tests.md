## ProgressionSettings — Квадратична формула

### PS-01 — `levelForXp(0)` = 1
- [ ] Виконано
- **Кроки:** Новий гравець без жодного контракту. Відкрити статистику.
- **Очікується:** Відображається рівень 1.

### PS-02 — `levelForXp(xp)` = 1 якщо xp < step(2)
- [ ] Виконано
- **Кроки:** Гравець виконав один F-ранг контракт (50 XP). XP менше порогу рівня 2 (300 XP).
- **Очікується:** Рівень залишається 1.

### PS-03 — `levelForXp(xp)` = 2 при точному порозі рівня 2
- [ ] Виконано
- **Кроки:** Гравець набирає рівно 300 XP (дефолт: xp-multiplier=100, xp-base=200 → step(2)=300).
- **Очікується:** Рівень стає 2.

### PS-04 — `levelForXp(xp)` не перевищує `maxLevel`
- [ ] Виконано
- **Кроки:** Гравець-адмін отримує більше XP, ніж потрібно на рівень 20.
- **Очікується:** Рівень зупиняється на 20; XP продовжує накопичуватись (потрібно для prestige).

### PS-05 — Лінійний fallback при `xp-multiplier: 0`
- [ ] Виконано
- **Кроки:** Адмін встановлює `xp-multiplier: 0` та `xp-per-level: 500` у contracts.yml. Гравець виконує контракти.
- **Очікується:** Кожні 500 XP = 1 рівень (лінійна прогресія).

### PS-06 — `xpNeededForLevel(1)` = 0
- [ ] Виконано
- **Кроки:** Перевірка порогу першого рівня в системі.
- **Очікується:** Рівень 1 вимагає 0 XP.

### PS-07 — `xpNeededForLevel(20)` > `xpNeededForLevel(19)`
- [ ] Виконано
- **Кроки:** Порівняти пороги рівнів 19 і 20.
- **Очікується:** Поріг 20-го рівня більший за 19-й (крива зростає).

### PS-08 — `defaults()` повертає валідний об'єкт без конфігу
- [ ] Виконано
- **Кроки:** Видалити або очистити `contracts.yml`. Перезавантажити плагін.
- **Очікується:** Плагін стартує без помилок; дефолтні значення застосовані.

## PlayerStats — XP та прогресія

### ST-01 — `addXp()` накопичує XP
- [ ] Виконано
- **Кроки:** Гравець виконує F-ранг контракт (base XP = 50). Переглянути статистику.
- **Очікується:** XP збільшується на 50.

### ST-02 — `addXp()` ігнорує від'ємні значення
- [ ] Виконано
- **Кроки:** Технічна перевірка: спроба передати від'ємне значення XP.
- **Очікується:** XP не змінюється; значення залишається невід'ємним.

### ST-03 — `addXp()` не зменшує XP нижче 0
- [ ] Виконано
- **Кроки:** Гравець з 50 XP отримує 0 XP (від'ємний input заблокований).
- **Очікується:** XP = 50, не менше 0.

### ST-04 — `incrementContractsCompleted()` збільшує лічильник
- [ ] Виконано
- **Кроки:** Гравець виконує перший контракт. Переглянути лічильник виконаних контрактів.
- **Очікується:** `contractsCompleted` = 1.

### ST-05 — `prestige()` скидає XP до 0
- [ ] Виконано
- **Кроки:** Гравець досягає рівня 20 та вводить `/contracts prestige`.
- **Очікується:** XP гравця скидається до 0; рівень стає 1.

### ST-06 — `prestige()` збільшує `prestigeLevel` на 1
- [ ] Виконано
- **Кроки:** Гравець з prestigeLevel=1 повторно досягає рівня 20 та prestige-ується.
- **Очікується:** `prestigeLevel` = 2.

### ST-07 — `setLastHighRankAt()` зберігає timestamp
- [ ] Виконано
- **Кроки:** Гравець виконує B-ранг контракт.
- **Очікується:** `lastHighRankAt` оновлюється до поточного unix-часу.

## ProgressionService — Логіка рівнів та prestige

### PS-SV-01 — `levelForXp()` делегує до ProgressionSettings
- [ ] Виконано
- **Кроки:** Гравець виконує кілька контрактів та накопичує XP вище порогу рівня 3.
- **Очікується:** `contractorLevel()` повертає 3.

### PS-SV-02 — `canPrestige()` = false якщо рівень < maxLevel
- [ ] Виконано
- **Кроки:** Гравець на рівні 15 вводить `/contracts prestige`.
- **Очікується:** Повідомлення `contracts.prestige-not-ready`; prestige не виконано.

### PS-SV-03 — `canPrestige()` = false якщо `prestigeLevel >= maxPrestige`
- [ ] Виконано
- **Кроки:** Гравець з prestige=5 (максимум) досягає рівня 20 та вводить `/contracts prestige`.
- **Очікується:** Повідомлення `contracts.prestige-max`; prestige не виконано.

### PS-SV-04 — `canPrestige()` = true при рівні 20 і prestige < max
- [ ] Виконано
- **Кроки:** Гравець досягає рівня 20 (prestige=0). Вводить `/contracts prestige`.
- **Очікується:** Prestige виконано успішно; повідомлення `contracts.prestige-success`.

### PS-SV-05 — `prestigeXpMultiplier(0)` = 1.0
- [ ] Виконано
- **Кроки:** Новий гравець (без prestige) виконує контракт.
- **Очікується:** XP нараховується без бонусу (×1.0).

### PS-SV-06 — `prestigeXpMultiplier(2)` = 1.10
- [ ] Виконано
- **Кроки:** Гравець з prestige=2 виконує F-ранг контракт (base 50 XP).
- **Очікується:** Нараховується 55 XP (50 × 1.10).

### PS-SV-07 — `applyCompletion()` нараховує масштабований XP
- [ ] Виконано
- **Кроки:** Гравець з prestige=1 виконує D-ранг контракт (base 250 XP).
- **Очікується:** Нараховується 263 XP (250 × 1.05, округлено вниз).

### PS-SV-08 — `applyCompletion()` оновлює `lastHighRankAt` для B/A/S
- [ ] Виконано
- **Кроки:** Гравець виконує B-ранг контракт.
- **Очікується:** `lastHighRankAt` оновлено до поточного часу.

### PS-SV-09 — `applyCompletion()` не оновлює `lastHighRankAt` для F/E/D/C
- [ ] Виконано
- **Кроки:** Гравець виконує C-ранг контракт.
- **Очікується:** `lastHighRankAt` не змінюється.

### PS-SV-10 — Сповіщення `prestige-ready` при досягненні рівня 20
- [ ] Виконано
- **Кроки:** Гравець виконує контракт, що переводить його з рівня 19 на 20.
- **Очікується:** У чаті з'являється повідомлення `contracts.prestige-ready`.

## ContractRankRoller — Зважений roll

### CR-01 — Roll не повертає ранги з нульовою вагою як пріоритетні
- [ ] Виконано
- **Кроки:** Гравець рівня 1 (вага S=0). Дошка генерує кілька офферів.
- **Очікується:** Жоден S-ранг оффер не з'явився серед стандартних слотів.

### CR-02 — Pity бонус для B/A/S при `rankedWithoutHigh >= threshold`
- [ ] Виконано
- **Кроки:** На дошці виконано 12 підряд контрактів без B/A/S. Генерується новий оффер.
- **Очікується:** Ваги B/A/S збільшені на 12; імовірність B+ значно вища.

### CR-03 — Pity бонус для A/S при `rankedWithoutElite >= threshold`
- [ ] Виконано
- **Кроки:** На дошці виконано 25 підряд контрактів без A/S. Генерується новий оффер.
- **Очікується:** Ваги A/S збільшені на 8.

### CR-04 — Pity лічильник скидається при B-ранзі
- [ ] Виконано
- **Кроки:** `rankedWithoutHigh` = 12. На дошці генерується та виконується B-ранг контракт.
- **Очікується:** `rankedWithoutHigh` скидається до 0.

### CR-05 — `allowedRanks` обмежує можливі ранги
- [ ] Виконано
- **Кроки:** Слот дошки обмежений рангами F/E/D. Генерується оффер для цього слота.
- **Очікується:** Оффер має ранг лише F, E або D — не вищий.

### CR-06 — Нульові ваги не потрапляють у roll
- [ ] Виконано
- **Кроки:** Конфіг задає вагу F=0 на рівні 20. Дошка з effectiveLevel=20 оновлюється.
- **Очікується:** F-ранг оффери не генеруються.

## SettlementProgress — Trust та project unlock

### SP-01 — `addTrustLevel()` збільшує trust_level
- [ ] Виконано
- **Кроки:** Гравець виконує рутинний контракт на дошці (trustPerRoutine=2).
- **Очікується:** `trust_level` дошки збільшується на 2.

### SP-02 — `addTrustLevel()` не опускає нижче 0
- [ ] Виконано
- **Кроки:** Технічна перевірка: передати від'ємний delta до trust.
- **Очікується:** `trust_level` залишається ≥ 0.

### SP-03 — `incrementRoutineCompletions()` збільшує лічильник
- [ ] Виконано
- **Кроки:** Гравець виконує рутинний контракт.
- **Очікується:** `routine_completions` збільшується на 1.

### SP-04 — `unlockProject()` додає project ID до списку
- [ ] Виконано
- **Кроки:** Гравець виконує PROJECT-контракт "bridge_project".
- **Очікується:** "bridge_project" з'являється у `unlocked_projects` дошки.

### SP-05 — `unlockProject()` не дублює існуючий ID
- [ ] Виконано
- **Кроки:** "bridge_project" вже є в `unlocked_projects`. Виконується той самий контракт вдруге.
- **Очікується:** Список не змінюється; дублікатів немає.

### SP-06 — `setActiveProjectId(null)` очищає активний проект
- [ ] Виконано
- **Кроки:** Гравець виконує активний PROJECT-контракт.
- **Очікується:** `active_project_id` стає null; нова генерація може запустити інший PROJECT.

### SP-07 — `hasActiveProject()` = false якщо activeProjectId = null
- [ ] Виконано
- **Кроки:** Дошка без поточного PROJECT-контракту.
- **Очікується:** Нова генерація може запропонувати будь-який PROJECT.

### SP-08 — PROJECT trigger не спрацьовує до мін-порогу trust
- [ ] Виконано
- **Кроки:** `trust_level` = 30, trigger вимагає `min-trust: 50`.
- **Очікується:** PROJECT-контракт не генерується; слот залишається рутинним.

### SP-09 — PROJECT trigger не спрацьовує до мін-порогу routine_completions
- [ ] Виконано
- **Кроки:** `routine_completions` = 50, trigger вимагає `min-routine-completions: 100`. Trust виконано.
- **Очікується:** PROJECT-контракт не генерується.

### SP-10 — PROJECT trigger спрацьовує при виконанні всіх умов
- [ ] Виконано
- **Кроки:** `trust_level` ≥ minTrust, `routine_completions` ≥ minRoutineCompletions, cooldown минув.
- **Очікується:** PROJECT-контракт з'являється на спеціальному слоті дошки.

## SettlementReputation

### SR-01 — `lifetimeCompleted` збільшується при виконанні контракту
- [ ] Виконано
- **Кроки:** Гравець виконує перший контракт на дошці.
- **Очікується:** `lifetime_completed` для цієї пари (гравець, дошка) = 1.

### SR-02 — `lifetimeCompleted` не скидається при зміні репутації
- [ ] Виконано
- **Кроки:** Гравець виконав 5 контрактів, після чого відмовився від 1.
- **Очікується:** `lifetime_completed` = 5; репутація змінилась, але лічильник виконаних — ні.

### SR-03 — Репутація не опускається нижче 0
- [ ] Виконано
- **Кроки:** Гравець з reputation=2 відмовляється від контракту (штраф −5).
- **Очікується:** reputation = 0 (не −3).

## StorageService — DB міграції

### DB-01 — Стара БД з `contract_xp` автоматично мігрує до `xp`
- [ ] Виконано
- **Кроки:** Запустити сервер з існуючою БД (старі назви колонок). Перевірити структуру таблиці.
- **Очікується:** Колонка перейменована; дані збережені; плагін завантажується без помилок.

### DB-02 — Стара БД з `completed_contracts` мігрує до `contracts_completed`
- [ ] Виконано
- **Кроки:** Та сама процедура, що і DB-01.
- **Очікується:** Дані збережені; лічильник контрактів не скинувся.

### DB-03 — Стара БД з `trust` мігрує до `trust_level`
- [ ] Виконано
- **Кроки:** Запустити сервер з існуючою БД settlement_progress.
- **Очікується:** trust_level коректно завантажується; дошки зберігають накопичений trust.

### DB-04 — Стара БД з `routine_completed` мігрує до `routine_completions`
- [ ] Виконано
- **Кроки:** Та сама процедура, що і DB-03.
- **Очікується:** routine_completions збережено; PROJECT trigger перевіряє коректне значення.

### DB-05 — Нова БД створюється з новими іменами колонок
- [ ] Виконано
- **Кроки:** Видалити `frontier-contracts.db`. Запустити сервер.
- **Очікується:** Нова БД має колонки `xp`, `contracts_completed`, `trust_level`, `routine_completions`.

### DB-06 — `last_high_rank_at` зберігається і завантажується
- [ ] Виконано
- **Кроки:** Гравець виконує B-ранг контракт. Перезавантажити сервер. Перевірити значення.
- **Очікується:** `lastHighRankAt` не скинулось; значення збережено в БД.

### DB-07 — `prestige_level` зберігається і завантажується
- [ ] Виконано
- **Кроки:** Гравець робить prestige. Перезавантажити сервер.
- **Очікується:** `prestigeLevel` = 1 після перезавантаження.

### DB-08 — `unlocked_projects` зберігається як JSON-масив
- [ ] Виконано
- **Кроки:** Гравець виконує PROJECT-контракт. Перезавантажити сервер.
- **Очікується:** PROJECT залишається в `unlocked_projects`; не генерується повторно як новий.

## ContractService — Інтеграція

### CS-PR-01 — Prestige-ready повідомлення при досягненні рівня 20
- [ ] Виконано
- **Кроки:** Гравець виконує контракт і досягає рівня 20 вперше.
- **Очікується:** В чаті з'являється `contracts.prestige-ready`.

### CS-PR-02 — Prestige-ready нагадує при кожному контракті на рівні 20
- [ ] Виконано
- **Кроки:** Гравець вже на рівні 20 (prestige ще не зроблено). Виконує ще один контракт.
- **Очікується:** Повідомлення `contracts.prestige-ready` з'являється знову як нагадування.

### CS-PR-03 — `/contracts prestige` — успіх
- [ ] Виконано
- **Кроки:** Гравець на рівні 20, prestige < max. Вводить `/contracts prestige`.
- **Очікується:** Повідомлення `contracts.prestige-success` з prestige_level та bonus_percent.

### CS-PR-04 — `/contracts prestige` — не вистачає рівня
- [ ] Виконано
- **Кроки:** Гравець на рівні 15 вводить `/contracts prestige`.
- **Очікується:** Повідомлення `contracts.prestige-not-ready`; жодних змін у статистиці.

### CS-PR-05 — `/contracts prestige` — досягнуто максимального prestige
- [ ] Виконано
- **Кроки:** Гравець з prestige=5 (maxPrestige=5) на рівні 20 вводить `/contracts prestige`.
- **Очікується:** Повідомлення `contracts.prestige-max`; prestige не виконано.

### CS-PR-06 — Ефективний рівень генерації враховує trust
- [ ] Виконано
- **Кроки:** Найкращий гравець рівня 10. Дошка має `trust_level`=50, `trust-level-divisor`=25 → trustBonus=2.
- **Очікується:** Генерація відбувається за таблицею рівня 12, а не 10.
